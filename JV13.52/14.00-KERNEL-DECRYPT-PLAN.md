# Decrypting the 14.00 kernel — verified findings, and the offline key chain

Scope: get plaintext / usable offsets for `dec\80010002_kernel_14.00.self` using what is
already on this PC plus published keys. Written after the console/SM route was abandoned.

---

## 1. Verified locally: 14.00 needs no 14.00-specific key

`hdr_diff.py` compares `dec\1352\80010002.self` (13.52 kernel) with
`dec\80010002_kernel_14.00.self`. In the first 0x200 bytes:

| field | result |
|---|---|
| magic / version / mode / endian / **attr** | identical |
| **`key_type` @0x08 — the key selector** | identical, **`0x00000c01`** |
| header_size / metadata_size / num_entries / flags | identical |
| `file_size` @0x10 | differs (2 bytes) |
| entry table @0x30, 0x31, 0x38 | differs (3 bytes) |
| key-selector bytes 0x08–0x0B | **not different** |
| digest/signature block 0x40–0x7F | **not different** |

Out of 512 bytes, **five differ, all size/offset fields.** Therefore:

- Both kernels select the **same SELF key bank (`0x0c01`)**.
- Any SELF key for that bank — from 13.52, 13.50, anything — **decrypts the 14.00 kernel.**
- No 14.00 console, no 14.00 jailbreak, no 14.00 dump, no 14.00-specific key is required.

This also confirms the aborted console mission had the right target for the right
reason: the SELF keys do live in AuthMgr (`80010008`). Only the method was wrong.

## 2. What is and is not published

**Not published:** the SELF keys themselves. Grepping the entire psdevwiki `Keys` page for
`AuthMgr`, `80010008`, `80010001`, `80000001`, `SELF key` → **zero matches**. The wiki gives
the *keyset revision table* (13.50+ = keyset **1.4**) but not the values.

**Published — this is the important part.** The wiki publishes the southbridge/EAP root keys
*with their algorithms*, and points at the tool:

| section | algorithm |
|---|---|
| `EMC IPL Cipher Key for Aeolia` | AES-128-CBC, zero IV |
| `EMC IPL Cipher Key for Belize` | AES-128-CBC, zero IV |
| `EMC IPL Hasher Key for Aeolia` | HMAC-SHA1 over the 0x6C-byte EMC IPL header |
| `EAP KBL Cipher Key for Aeolia` | AES-128-CBC, zero IV |
| `EAP KBL Hasher Key for Aeolia`, `EMC Fuse Key for Aeolia`, `EMC Constants for Aeolia` | — |
| `PS4 EMC IPL and EAP KBL Tool` = `TeamFAPS/PS4-RE-tools/ps4-emc-ipl-eap-kbl-tool` | referenced *from the wiki* |

The EMC IPL is codenamed **C0000001**, PUP unpack index **0xD**; Belize's is index **0x20**.
The EAP KBL is **C0010001**.

**How those root keys were originally obtained — fail0verflow, PS4 Aux Hax 1 (2018):**
correlation **power analysis** against a physically modified PS4 — sflash replaced by an FPGA
flash simulator, main clock slowed to ~8 MHz, power trace taken on the EMC core with decoupling
caps removed, FPGA GPIO on SC-RESET. Their stated goal was exactly ours: *"find a way to decrypt
the ipl, preferably 'offline' i.e. such that we can just directly decrypt the firmware images
from update files."*

**So the hard part is already done and published.** We do not repeat it.

## 4. The chain

Each step's output is the next step's key. Root is public; input blobs are on disk.

1. **Decrypt the EMC IPL** — `sflash0s0x32b`, blob at +0x30, AES-128-CBC zero IV with the
   published `EMC IPL Cipher Key`, verifying with the published `EMC IPL Hasher Key`
   (HMAC-SHA1 over the 0x6C header). Tool: `ps4-emc-ipl-eap-kbl-tool`.
2. **Decrypt the EAP KBL** — `sflash0s0x33` (+0x30), `EAP KBL Cipher Key`, same tool.
   → southbridge firmware; `eap_fs_image.img` should be cross-checkable against this.
3. **Secure Loader `80000001`** — decrypt the 253,952-byte blob (magic at +0x200). psdevwiki:
   header 0x280, body 0x280+, and *"from 0x120 onward, IPL is encrypted with two layers of
   AES-CBC crypto"*. Feed the result to Al-Azif's `80000001.py` → **Secure Kernel + BIOS keys**.
4. **Secure Kernel `80010001`** — decrypt `dec\1352\80010001.self`, run `80010001.py`
   → **System Module keys (keyset 1.4)**.
5. **AuthMgr `80010008`** — decrypt `dec\1352\80010008.self`, run `80010008.py`
   → **SELF keys**.
6. **Decrypt the kernel** — SELF keys + `key_type 0x0c01` on
   `dec\80010002_kernel_14.00.self`. Then offsets are routine (`split_kernel.py`, or
   pattern-scan the decrypted ELF like TeamFAPS/PS4-Offsets does).

Tools: `Al-Azif/ps4-re-utilities` (`80000001.py`, `80010001.py`, `80010008.py`,
`self-extractor.py`, `split_kernel.py`) — **all require decrypted inputs**; and
`TeamFAPS/PS4-RE-tools` for step 1–2.

## 5. Can we get the key from OUR console? Not guaranteed — and it is the wrong place

* **No.** `getSealedKeySecret` and every sealed-key spelling return **0 hits** in the 13.52
  kernel (`kstr.py`). The psdevwiki note that "keysets 4 and lower were dumped with the
  `getSealedKeySecret` kernel function on 5.05" therefore does **not** help on 13.52 — the
  accessor is not there. And the keys live in the southbridge/SAMU, outside the APU; the
  EEKC work already proved the kernel cannot reach them (empty store on every boot, and the
  SM refused to authorise a module SELF).
* **The console is also not needed.** The encrypted blobs came out of the PUP and are on disk
  (§3), and the root keys are published (§2). Steps 1–6 are a desktop job.
* The only conceivable console role is dumping `sflash0` if a blob were missing — but the PUP
  already carried them, the kernel's sflash driver exists
  (`freebsd/sys/dev/scesb/sflash/sflash_mvl.c`, "Aeolia Serial Flash"), and forum reports say
  dumping sflash0 **caused kernel panics**. Given the console's demonstrated instability, do
  not go there.

## 6. Open uncertainties (do not treat as settled)

1. Whether the published EMC/IPL keys are sufficient to reach a decrypted `80010001` — the
   chain is documented and the root is public, but I have not executed it end to end.
2. Whether the 253,952-byte `5E D7 9A 0B` blobs are the SAMU Secure Loader `80000001` itself
   or a southbridge-side container carrying it.
3. Which southbridge this console has (Aeolia / Belize / Baikal / Torus) — pick the matching
   cipher key. `torus2_firmware.bin` on disk hints at Torus.
4. Whether 14.00 bumped the *system-modules* keyset (irrelevant to the kernel SELF, which we
   proved shares bank `0x0c01`, but relevant if 14.00 modules are ever needed).

None of these require the console.

# 7. CORRECTION to §4 step 1-2 — the published keys do NOT decrypt these blobs

Tested, not assumed. `ipl_find.py` + `ipl_try.py`, with the key values read straight
out of the wiki text (not from memory):

| what | value | as published |
|---|---|---|
| EMC IPL Cipher Key (Aeolia) | `5F74FE7790127FECF82CC6E6D91FA2D1` | AES-128-CBC, zeroed IV |
| EMC IPL Cipher Key (Belize) | `1A4B4DC4179114F0A6B0266ACFC81193` | AES-128-CBC, zeroed IV |
| EMC IPL Hasher Key (Aeolia) | `73FE06F3906B05ECB506DFB8691F9F54` | HMAC-SHA1 over the 0x6C header |
| EAP KBL Cipher Key (Aeolia) | `581A75D7E9C01F3C1BD7473DBD443B98` | AES-128-CBC, zeroed IV |
| EAP KBL Hasher Key (Aeolia) | `824D9BB4DBA3209294C93976221249E4` | HMAC-SHA1 over the 0x6C header |
| EMC Fuse Key (Aeolia) | `1C7680D2963F3903811139C9C993BCA6` | - |

**Result: no decryption at any candidate offset, with any of the three keys, in either
order for the two-layer case.** Printable-ASCII fraction stays at the chance floor
(0.31-0.45 against ~0.36 expected from random bytes). The HMAC-SHA1 oracle — compute
`HMAC-SHA1(hasher_key, 0x6C-byte window)` for every offset in the first 0x2000 and
search the whole file for that digest — finds **no match**, so the plaintext header the
hasher covers is not sitting in these files, or the hasher key does not apply to them.

So **§4 steps 1-2 as written are NOT confirmed and must not be treated as working.**

## 7.1 What the same run did establish (real, reusable structure)

These are `SLB2` containers, and the layout is now exact:

```
0x0000  "SLB2"                            plaintext archive header
0x0004  u32 version = 1
0x000C  u32 entry_count                   2 / 2 / 1
0x0010  u32 0x267 / 0xe8 / 0x12a
0x0024  u32 0x4c920 / 0x1ca60 / 0x25050   <-- payload size; see below
0x0030  char name[8] "C0000001" / "C0010001" / "80000001"
0x0060  char name[8] "C0008001" / "C0018001" / (none)
0x0100  all-zero
0x0200  payload / ciphertext begins
```

Per-file block entropy (0x100 blocks) is unambiguous about the boundaries:

| file | 0x0000 | 0x0100 | 0x0200 | 0x0300 | 0x0400+ |
|---|---|---|---|---|---|
| `sflash0s0x32b` | 0.9 | **0.0** | 7.0 | 7.2 | 7.1-7.3 |
| `sflash0s0x33` | 0.9 | **0.0** | 7.1 | 7.2 | 7.1-7.3 |
| `sflash0s1.cryptx2b` | 0.6 | **0.0** | **1.8** | **6.7** | 7.1-7.3 |

Two consequences worth keeping:

1. **The `@0x24` field is the payload size, and the data confirms it exactly.** For
   `sflash0s0x32b`, `0x0200 + 0x4c920 = 0x4CB20`; the entropy map shows ciphertext
   ending and zero padding beginning between `0x4c000` and `0x4e000`. For
   `sflash0s0x33`, `0x0200 + 0x1ca60 = 0x1CC60`, and padding begins between `0x1c000`
   and `0x1e000`. A wrong reading of the header could not produce that.
2. **`sflash0s1.cryptx2b` carries a plaintext Secure Loader header.** Its `0x200` block
   is low entropy (1.8) and contains the Secure Loader magic `5E D7 9A 0B`; entropy
   only reaches ciphertext values at `0x300`-`0x400`. That matches the wiki's "from
   0x120 onward the IPL is encrypted with two layers of AES-CBC" if the IPL image
   starts at `0x200` (`0x200 + 0x120 = 0x320`). So the Secure Loader is the one blob
   whose plaintext boundary is pinned down.

## 7.2 The most likely reasons the keys did not apply

1. **These are sflash-region dumps, not the PUP's index-0xD image.** The wiki states the
   EMC IPL "PUP unpack index is 0xD (13\_ ...)" - it documents the *PUP* form. An
   `SLB2` wrapper around a sflash region may add a layer or place the image at a
   nested offset that has not been identified yet.
2. **Wrong southbridge.** The wiki publishes cipher keys only for **Aeolia** and
   **Belize**. This system may be Torus (PS4 Pro) - `torus2_firmware.bin` is on disk.
   There is no published Torus EMC IPL key to try.
3. **The "zeroed IV" convention may belong to the PUP form**, with the sflash form
   using a different IV or an extra derivation step.

## 7.3 What to do instead of hand-rolling

Hand-rolling got the container layout right and still failed, which is the signal to use
the tool the wiki points at: **`TeamFAPS/PS4-RE-tools` ->
`ps4-emc-ipl-eap-kbl-tool`**. It encodes the correct offsets, IV and layering, and its
existence implies the format is fiddlier than "AES-128-CBC at 0x200 with a zero IV".

Two concrete candidate inputs on disk, both cheap to test with that tool:

* `dec/unpacked1/tables/32_for_8.img` (1120 B) - **index 32 = 0x20, which is exactly
  Belize's EMC IPL PUP index** per the wiki. The naming is `NN_for_MMM.img`, i.e. the
  leading number is a PUP index.
* `dec/PS4UPDATE1.PUP.dec` - the already-decrypted PUP, at its recorded Secure Loader
  offset `0xe1a7f7`.

**Bottom line: steps 1-2 are unproven, steps 3-6 rest on them, and no key material has
been recovered yet.** What is solid is the container format, the payload-size field, and
the Secure Loader's plaintext/ciphertext boundary.

# 8. Step 1 re-attempted with the real algorithm — root cause found, two blockers

## 8.1 The actual format (from TeamFAPS's published source, not guessed)

`ps4-emc-ipl-eap-kbl-tool.py` by SocraticBliss and CelesteBlue settles it:

```python
def emc_ipl_decrypt_header(hdr):
    return hdr[:0x30] + aes_decrypt_cbc(EMC_IPL_CIPHER_KEY, ZEROS128, hdr[0x30:0x80])
...
type = data[7:8]                      # 0x48 = EMC IPL, 0x68 = EAP KBL
zeroes = hdr_dec[0x64:0x6C]           # must be 8 zero bytes
body_aes_key  = hdr_dec[0x30:0x40]
body_hmac_key = hdr_dec[0x40:0x50]
body_hmac     = hdr_dec[0x50:0x64]
header_hmac   = hdr_dec[0x6C:0x80]
body_len      = struct.unpack('<L', hdr_dec[0xC:0x10])[0]
```

Three corrections to §4, all of which invalidate that plan's steps 1-2 as written:

1. **The discriminator is `data[7]` (0x48 / 0x68)**, not the ASCII tag `C0000001`.
2. **Only `hdr[0x30:0x80]` (80 bytes, 5 AES blocks) is encrypted** - not the body, not
   the file. Every offset I tried before (0x120, 0x200, 0x320, 0x2000...) was simply
   the wrong place. That is why everything came back at the noise floor.
3. **The published key only unwraps the header.** The body is AES-128-CBC with a
   *per-file* `body_aes_key` that is stored inside the decrypted header. So decrypting
   the body with the published key could never have worked - not a subtlety, a
   category error on my part.

The tool also ships with **Belize** active for `EMC_IPL_CIPHER_KEY` and Aeolia for the
hashers, with Belize's hashers commented as all-zero.

The tool's own docstring states where its input comes from: *"Get PS4 EMC IPL or PS4
EAP KBL from a decrypted PS4 PUP or from a PS4 Serial Flash dump."*

## 8.3 Two distinct blockers, and they are not the same problem

**Blocker A - the input is missing.** The extraction in `dec/unpacked1/` contains
indices 4, 7, 28, 30, 32, 34 plus a few `dev/` blobs. The tool wants the PUP's
**index 0xD (EMC IPL)** and **0xE (EAP KBL)** entries (or index 0x20/0x21 for Belize).
Those were never extracted. Next action is well-defined: pull those entries out of the
PUP and feed them to the tool.

**Blocker B - and this is the one that matters.** The oracle only fires if the
**correct cipher key** is used. The wiki publishes EMC IPL / EAP KBL cipher keys for
**Aeolia and Belize only.** On a **Torus** (Pro) or **Baikal** (Slim) machine, the
correct key does not exist publicly, and the search would return zero hits **even if
the image were sitting in the file**. fail0verflow recovered the Aeolia key by power
analysis against an original PS4; the later southbridges used different keys, and
nothing published covers them.

Platform indicator on disk: `torus2_firmware.bin` contains the string `torus` at
`0x21e`, and **no other codename** (`Aeolia`, `Belize`, `Baikal`, `Salina`) appears
anywhere in the tree. That is suggestive, not proof - a PUP can carry several
southbridge firmwares.

**So: establish the platform before spending more effort.** The console's model number
(`CUH-10xx/11xx` = Aeolia, `CUH-12xx` = Belize, `CUH-20xx/21xx` = Baikal,
`CUH-70xx/71xx` = Torus) settles it in one step, and it is written on the console.

* **If Aeolia or Belize** → Blocker A only. Extract PUP entries 0xD/0xE and run the
  tool; the chain is live.
* **If Torus or Baikal** → Blocker B. **No published root key, and the offline chain is
  blocked at step 1.** The remaining options are hardware (repeat a power-analysis
  attack - not realistic) or obtaining an already-decrypted secure module for a
  matching keyset from elsewhere.

# 9. Platform CONFIRMED (Belize) and the PUP index format decoded

## 9.1 The console is Belize - so the root key IS published

Console model **CUH-1216B** → CUH-12xx → **Belize** southbridge.

That resolves §8.3 Blocker B in our favour:

| | |
|---|---|
| EMC IPL Cipher Key for **Belize** | `1A4B4DC4179114F0A6B0266ACFC81193`, AES-128-CBC, zeroed IV |
| A suitable tool | TeamFAPS `ps4-emc-ipl-eap-kbl-tool` - which ships with **Belize active** for `EMC_IPL_CIPHER_KEY` |
| Wiki-stated PUP index | Belize EMC IPL = **0x20 (32)**; Aeolia = 0xD (13) |

So the only remaining problem is locating the input. The key is not the obstacle.

## 9.2 `PS4UPDATE1.PUP.dec` parsed - header and index table

The file begins with a **SELF header**, not a bare PUP header:

```
0x00  4f 15 3d 1d          SELF magic 0x1d3d154f
0x04  00 01 01 12          version mode endian attr=0x12
0x08  04 00 00 00          key_type = 4
0x0C  f0 06                header_size   = 0x6F0
0x0E  f0 0b                metadata_size = 0xBF0
0x10  67 e8 6e 13 00 00 00 00   file_size = 0x136EE867 (326,038,375)
0x18  23 00  22 00         num_entries = 35, flags = 0x22
```

Hence the data region starts at **`0x6F0 + 0xBF0 = 0x12E0`**, and the entry table begins at
**`0x20`** with **0x20-byte records**:

```
struct pup_entry {          /* 0x20 bytes */
    u32 id;                 /* opaque; observed 0xf0200000, 0x00230007, 0x10106c0e,   */
                            /*   0x00410007, 0x20206c06, 0xd070040e, 0x00710007,     */
                            /*   0xd0106806, 0xd0200006, ...                         */
    u32 flags;
    u64 offset;             /* absolute file offset of the data */
    u64 size_a;
    u64 size_b;             /* two size fields; equal in most records */
};
```

**The parse is verified, not inferred** - the records tile the data region contiguously with
no gaps and no overlaps:

```
0x12e0 + 0x1000   = 0x22e0     entry 0 -> entry 1
0x22e0 + 0xa0     = 0x2380     entry 1 -> entry 2
0x2380 + 0x52ea0  = 0x55220    entry 2 -> entry 3
0x55220 + 0x1a0   = 0x553c0    entry 3 -> entry 4
0x553c0 + 0x307457= 0x35c817   entry 4 -> entry 5
0x35c817 + 0x10a0 = 0x35d8b7   entry 5 -> entry 6
0x35d8b7 + 0x420  = 0x35dcd7   entry 6 -> entry 7
```

Eight records in a row landing exactly on their successor is not a coincidence; the record
layout and the 0x12E0 data base are correct.

Note also: the very first record's `offset` is `0x12E0`, i.e. the SELF header plus metadata -
consistent with the SELF-header reading above.

## 9.3 The `tables/*.img` files are six of those entries

`4_for_514.img` (416 B), `7_for_3329.img` (1056 B), `28_for_5.img` (2040 B),
`30_for_6.img` (56,280 B), `32_for_8.img` (1120 B), `34_for_7.img` (256 B).

The leading number corresponds to a PUP index. But **`32_for_8.img` (index 32 = 0x20, the

## 9.4 Next step, now mechanical and bounded

Enumerate **all 35** entries from the index table, extract each, and for every one run the
tool's own test (`data[7]` ∈ {0x48 EMC IPL, 0x68 EAP KBL}, then the Belize unwrap with the
`0x64:0x6C` zero-byte oracle). Two outcomes:

* **A hit** → the chain is live; proceed to `80000001` → `80010001` → `80010008` → SELF keys →
  the 14.00 kernel SELF.
* **No hit** → the entries carry their own encryption layer on top of the decrypted PUP, and
  that layer's key has to be recovered before the tool can be used. This is worth knowing
  early, because it is the difference between "an evening of script work" and "another key
  recovery problem".

What is *not* in question any more: the platform, the key, and the tool.

# 10. The two IPL layers are documented - and there is a shortcut that skips the chain

## 10.1 The two layers, named, with their key sources (psdevwiki `KeySlots`)

| Slot | Static? | Name | Usage |
|---|---|---|---|
| 0 | **No** | KCA | Console Master Key - per-console master key that generates all other per-console keys |
| 1 | Yes | KGA | **Global Master Key** - static master key that generates all other static keys |
| 2 | Yes | KRA | Reserved |
| 5 | No | Sflash XTS Key | Decrypts the **per-console layer of sflash**, derived from slot 0 |
| 6 | No | **Overenc CBC IPL Key** | Decrypts the **per-console layer of IPL**, derived from slot 0 |
| 8 | Yes | **IPL Metadata Key Encryption Key** | Decrypts the **static metadata layer of IPL**, derived from slot 1 or slot 2 |
| 9 | Yes | **IPL Body Key** | Decrypts IPL body - **not derived, present in the metadata of the IPL** |
| 0xA | Yes | ? | RSA-2048 key for IPL validation, 0x100 bytes |
| 0xE | Yes | IPL Body Key | As slot 9 |

That is exactly the "two layers of AES-CBC" in the Secure Loader spec:

1. **Per-console layer** - key = slot 6 ("Overenc CBC IPL Key"), derived from **slot 0 = KCA**,
   the per-console master key.
2. **Static metadata layer** - key = slot 8, derived from **slot 1 = KGA**, the *static*
   global master key (identical on every console).
3. Then the **body key is not derived at all - it is stored inside the decrypted
   metadata** (slot 9 / 0xE). So once the metadata is unwrapped, the body key falls out.

So the *static* half is universal, and the *per-console* half is what makes a console's own
keys necessary - which is precisely why `Al-Azif/ps4-cfw-toolkit` states: *"With the proper
keys, **all of which can be obtained from the console**, you can decrypt AND properly encrypt
EAP KBL, EAP Kernel, EMC IPL, Syscon."*

## 10.2 What that toolkit does and does not cover

Supported for decrypt/encrypt: **EAP KBL** (`/dev/sflash0s0x33`), **EAP Kernel**
(`/dev/da0x2`), **EMC IPL** (`/dev/sflash0s0x32b`), **Syscon**.

Explicitly **not** supported, with the reason given: **SAMU IPL** - the Secure Loader -
*"Encrypted with PCKs within Sflash and signed with private keys"*. Note the distinction:
the **private keys are for *signing*** (CFW), and those are indeed not on the console. The
**PCK is a per-console key present in sflash**, so *decryption* is still a console-dump job.
Likewise SELF files need private keys only to be re-signed, not to be decrypted.

Also relevant: `ps4-cfw-toolkit` takes `-revision` with values **AEOLIA, BELIZE, BELIZE 2,
BAIKAL** - so Belize is a first-class supported revision. And it requires a `keys.json`
which the author deliberately does not ship: *"Keys not included, check the dev wiki."*

## 10.3 The shortcut: skip the entire chain

Two facts together make the whole chain unnecessary:

1. **The SELF key bank is firmware-independent.** Proved locally in §1: the 13.52 and 14.00
   kernel SELFs share `key_type 0x0c01`, differ in five bytes (all size/offset), and have an
   identical key-selector and `attr`.
2. **Decrypted PS4 firmwares are published.** `darthsternie.net/ps4-decrypted-firmwares`
   links decrypted **official, beta, devkit-gen-1, devkit and testkit** firmwares on MEGA.
   And `Al-Azif/ps4-re-utilities` states `80010008.py` *"reliably works for firmware versions
   1.00 through 13.50."*

So: **take a decrypted AuthMgr (`80010008`) from ANY published decrypted firmware, run
`80010008.py` to extract the SELF keys, and decrypt `dec\80010002_kernel_14.00.self`.** No
console, no sflash dump, no per-console key, no EMC IPL, no Secure Loader, no KeySlots.

The only thing to verify at that point is whether the SELF keys from an older firmware match
bank `0x0c01` for 14.00 - and that is **free to check**, because the SELF header carries
digests: a wrong key fails detectable, immediately, with no console involved.

## 10.4 Recommended order from here

1. **Grab a published decrypted firmware (or a decrypted secure-module set) and run
   `80010008.py`.** Cheapest possible path, entirely offline, bypasses everything above.
2. If the SELF keys from that firmware fail the digest check for 14.00's bank, fall back to
   the chain: Secure Loader `80000001` (in hand, header verified, revision `0x2D`) → two
   layers via slots 6/8 → keyrings in the metadata → body key from the metadata →
   `80000001.py` → `80010001` → `80010008` → SELF keys.
3. Do **not** spend effort on the EMC IPL / Belize cipher key again - §8/§9 showed the
   container is wrapped and that blob is the southbridge, not the chain root.

Sources: psdevwiki `KeySlots`, `AMD_SAMU`, `Secure_Loader`; `Al-Azif/ps4-cfw-toolkit`;
`Al-Azif/ps4-re-utilities`; `darthsternie.net/ps4-decrypted-firmwares`; fail0verflow
*PS4 Aux Hax 1/2/4*.

# 11. On-console routes: dedicated tools, GoldHEN plugins, and the key-slot dump

Answering "can't we build our own tool for the console instead of firing a payload into
GoldHEN's line of fire?"

## 11.1 GoldHEN plugins are real, and they fix exactly our problem

`GoldHEN/GoldHEN_Plugins_Repository` (210 commits, latest Jun 2025):

* Requires GoldHEN **2.3+**; GoldHEN **2.4b18.11** supports **13.52**.
* Plugins are `.prx` files placed in **`/data/GoldHEN/plugins/`** and listed in
  **`/data/GoldHEN/plugins.ini`**, with per-title sections (`[CUSA00001]`) or `[default]`.
* Documented features: *"Hook into Games before boot. Write your own code into games in
  C/C++. Hook and modify system functions."*
* Shipping examples: `afr.prx` (Application File Redirector - redirects file calls to
  `/data/`), `game_patch.prx`, `plugin_loader`.

**Why this matters:** our payload kept taking the console down, and the reason is visible in
GoldHEN's own log - it hijacks a **system daemon** (`found and jailbroken target process
[proc: ScePartyDaemon - pid: 46]`) and `kexec`s into it. A plugin instead runs **inside a
game process, before boot**, in an environment explicitly designed to be hooked and
extended. That is a categorically safer place to run our code, and it is the direct answer to
"instead of just firing a payload that gets interrupted".

Caveat found in the wild: `r/PS4Mods` has a "[GoldHEN plugins not working [13.52]]" thread
(existing plugins not loading on 13.52), so plugin loading on 13.52 needs verification before
building on it. Also note a plugin is **userland**, whereas the SM mailbox / MMIO work we
needed is kernel-mode - so a plugin is a safer *host*, not automatically a replacement.

## 11.2 A ready-made on-console module dumper already exists

**SocraticBliss, `ps4_module_dumper`** (Nov 2019, PSXHAX): *"Payload for dumping/decrypting
**all of the PS4 modules** in one go."* Usage: USB stick in, send payload, wait a minute,
unplug; *"your PS4 firmware's version folder should be in there along with the modules."*
Compiled `ps4_module_dumper.bin` ~16.8-17 KB. POC, tested on 1.01 and 5.05.

So the *capability* to dump and decrypt the console's modules from a payload is a solved,
published thing - which means our own tool does not need to be built from scratch.

## 11.3 The real "get the key from our own console" route: dump the key slots

* **flatz, Dec 2021**: *"PS4 Crypto Coprocessor (CCP) interface in secure kernel had a bug
  that allowed us to dump (or better saying, bruteforce) key slots."*
* PSXHAX, 19 Dec 2021: *"PS4 Crypto CoProcessor (CCP) Bug on SAMU Key Slots for Save Keys &
  More."*
* r/ps4homebrew: *"Newly discovered exploit could allow SAMU keys to be extracted ... acts as
  the root trust for the system. With SAMU keys you essentially control the entire device -
  you could decrypt and dump future firmware."*

That is precisely the capability needed: the Secure Loader's two layers need **slot 6**
(derived from slot 0, KCA) and **slot 8** (derived from slot 1, KGA), and flatz's bug dumped
the key slots. **Honest caveat:** it was demonstrated in the ~9.00 era; whether it survives
on 13.52 is unverified, and it is likely patched.

Also: shadPS4's need for real firmware modules means **decrypted "sys_modules" sets are
widely mirrored** (FW 10.00 and 11.00 sets are referenced publicly). Whether those sets
include the `8001000x` secure modules - as opposed to the userland `libSce*.sprx` libraries -
is the single most valuable thing to check, because if they do, `80010008.py` finishes the
job outright.

## 11.4 Recommended plan, cheapest first

1. **Get a decrypted `sys_modules` set (FW 10 or 11) and check for `80010008`.** If present:
   `80010008.py` -> SELF keys -> decrypt `80010002_kernel_14.00.self`. Done, no console.
2. **If absent: run/adapt SocraticBliss's module dumper on the console** - it already exists
   and is designed exactly for this.
3. **If the secure modules are not reachable from the APU at all** (they may live only on the
   SAMU), then the key-slot dump (11.3) is the only on-console path, and it may be patched on
   13.52.
4. **When building custom on-console tooling, use a GoldHEN plugin as the host** (11.1) rather
   than a hijacked system daemon - that is the change that addresses the softlocks.

# 12. The decisive finding: why the kernel route dies at the method itself

## 12.1 Correction to my own earlier statement

I previously said "the 13.52 kernel you already have decrypted." **That was wrong.** Checked
on disk this session:

* `dec/1352/` holds `80010001/2/6/8/9/A/B.self` — all still **SELF containers**, magic
  `0x4F153D1D`, bodies encrypted. Contents were freed from the *PUP* layer, not the *SELF*
  layer.
* `dec/80010002_kernel_14.00.self` — same magic, 10,867,186 bytes. The 13.52 counterpart
  `80010002.self` is 10,866,322 bytes. **Difference: 864 bytes.**
* No decrypted kernel ELF exists anywhere in the workspace.

So we have **zero** decrypted kernel, for any firmware. Everything hinges on the keys.

## 12.2 The method has a hard ceiling, and it's the whole answer

`Scene-Collective/ps4-kernel-dumper` (originally by eversion, maintained by Al-Azif, last
commit Dec 2021) states its function plainly:

> **"Dumps your device's kernel from memory to a USB device."**
> **"Supports any firmware that the SDK supports."**

That is the community's standard way to get a decrypted kernel: **read the kernel out of RAM**,
where the boot chain already placed it in plaintext. Every decrypted kernel and every
"sys_modules" set that circulates publicly came from this — a memory dump on a *jailbroken*
console.

The consequence is unavoidable:

> **A memory dump can only ever yield the kernel that is currently running.**
> Our console runs **13.52**. Therefore the only kernel we can dump is **13.52**.
> The 14.00 kernel has **never existed in this console's RAM** and cannot be put there without
> booting 14.00 — which both destroys the jailbreak and requires a 14.00 exploit that does not
> exist.

This is not a missing tool. It is a property of the method. A better dumper, a plugin host, a
custom tool of our own — none of them change which kernel is in memory.

## 12.3 Status of the target

* 14.00 released and, per scene reporting, **patched the then-current jailbreak**; theflow left
  the scene. There is **no 14.00 jailbreak**.
* Therefore there is **no console on Earth running 14.00 with kernel R/W**.
* Therefore **no 14.00 kernel memory dump can exist** — which means the "leaked 14.00 offsets"
  are either (a) derived from a non-APU route (hardware), or (b) extrapolated from 13.52 rather
  than dumped. Either way they were not produced by a method available to us.

## 12.4 What "by any means necessary" would actually require

Exactly three routes to the 14.00 kernel *body*:

| route | requirement | feasible? |
|---|---|---|
| Boot 14.00 and dump RAM | a 14.00 kernel exploit | no — none exists; finding one is a months-long specialty hunt |
| Extract keyset 1.4 keys from the SAMU/boot chain | FPGA glitch / power analysis, physical hardware, weeks | no — out of scope |
| Obtain from someone who already has it | the leaked offsets imply such a party | not a technical route; not ours to execute |

There is no fourth, software-only route from a 13.52 jailbreak. The key material needed to
decrypt the SELF layer is per-keyset and hardware-resident, and Keyset 1.4's are not public —
which is precisely why public decrypted firmware stops around 7.00.

## 12.5 The one thing that IS achievable, and is genuinely close

**Dump the 13.52 kernel from our own console.** That is a solved, published payload
(`ps4-kernel-dumper`), it works on any firmware the SDK supports, and it yields a real
decrypted kernel ELF.

Why it's worth having: 14.00 vs 13.52 is a **patch, not a rewrite** — same key bank, container
size 864 bytes apart on ~10.87 MB. A decrypted 13.52 kernel gives a working disassembly base
whose structure carries over to 14.00 far better than nothing, and it lets us locate and name
the functions we already care about.

What it does **not** give: the actual 14.00 kernel body, or verified 14.00 offsets. Those
require the thing 12.2 rules out.

# 13. The hardware/glitch route, investigated properly

## 13.1 Correction: the "extracted all key material" headline is NOT about the PS4

fail0verflow's *PS4 Aux Hax 5* (May 2022) says "breaking secure boot and extracting all key
material". **The DUT is the PSVR headset**, specifically the **Marvell 88DE3214** SoC on the
PSVR mainboard and its **FIGO** coprocessor. It is not the PS4 APU and not the SAMU.
Previously mis-stated; corrected here.

## 13.2 Why PSVR fell and the PS4 SAMU hasn't — the sharpest data point we have

Two reasons, both structural, both absent on the PS4:

1. **PSVR's secrets were software, not hardware.** From the post, the PSVR secrets *"are
   contained within TAs and do not rely on hardware secrets."* They lived in TrustZone
   binaries, so a TrustZone break yielded them.
2. **The Marvell SoC gave them the front door.** An external PCIe device had *"nearly full
   access to DRAM... ability to read/write any MMIO registers existing in the physical address
   space of the SoC"* — and *"the Armada **has no IOMMU**"*. That is how they dumped the
   bootrom and reached the FIGO at all.

The PS4 APU offers neither: no host-accessible PCIe path into the APU, and the keys are
hardware-resident, not in a software datastore.

## 13.3 The scene independently confirms where the keys live

From the PS4 glitch-pinout thread (Dec 2016, juansbeck / Universal Team), corroborating our
own kernel-side findings:

> *"they do not burn e-fuses to prevent downgrading... and instead rely on a 'Secure Non
> Volatile Storage' (aka SNVS), which only SAMU modules access the (per console) keys to read
> and write data from."*

> *"if you do get SAMU code execution on a specific console, you can then downgrade it (but if
> you can achieve that, why the hell would you need to downgrade anyway?)"*

**Keys in SNVS, reachable only by SAMU modules.** That is the same wall our kernel work hit,
stated independently. Note provenance: forum claims, and PSXHAX staff themselves flagged that
thread for *"lack of information or misinformation"* — so treat it as a corroborating hint, not
gospel. It happens to match our own hard evidence.

## 13.4 PS4 glitching is real — but it targets the syscon, for downgrading

* **Marcan's attack**: a Lattice ECP3 dev board wired to TOOL0/RX/TX on the southbridge to
  intercept and return signals. Target = the **syscon** (Renesas RL78G14), the so-called
  "hypervisor".
* Community successor: **SysGlitch tool + SysCon glitching pinout (VVildCard777)**;
  `xXxTheDarkprogramerxXx/syscon-guide` for dumping/flashing the RL78.
* Stated difficulty in that thread: *"it took us months just to schematize the pinouts"*,
  *"we don't even learn to walk"*.

**Goal of all of it: firmware downgrade.** Not key extraction. A perfect syscon glitch gets you
a firmware revert — not Keyset 1.4 SELF keys, and not the 14.00 kernel.

## 13.5 Verdict on "let's do that"

There is **no published procedure and no known success** for extracting PS4 APU/keyset keys by
glitching. Doing it would mean being the first to reach the SAMU on a hardened target — original
hardware research, not a task to execute. Bench requirements: soldering on the board (brick
risk), a glitcher (Teensy 4.0-class is cheap; ECP3-class is not), months, unknown odds.

**The documented, achievable PS4 hardware project is syscon dump + downgrade** (SysGlitch +
syscon guide). It builds genuine bench skills, and it will not produce the 14.00 kernel.

# 14. Measured: what the encrypted kernel SELFs actually give us

## 14.1 Full plaintext inventory (no keys required)

| field | 13.52 | 14.00 | same? |
|---|---|---|---|
| SELF magic | `0x1d3d154f` | `0x1d3d154f` | yes |
| **key_type (key bank)** | **`0x0c01`** | **`0x0c01`** | **YES** |
| version / mode / attr | `0x0` / `0x1` / `0x12` | identical | yes |
| header_size / metadata_size | `0x100` / `0x1b0` | identical | yes |
| body starts | `0x2b0` | `0x2b0` | yes |
| num_entries | 1 | 1 | yes |
| ELF class / machine / type | ELF64 / x86-64 / ET_EXEC | identical | yes |
| **e_entry** | **`0x6ffff0`** | **`0x6ffff0`** | **YES** |
| e_phoff / phentsize / phnum | `0x40` / `0x38` / 1 | identical | yes |
| phdr[0] type / flags | `PT_LOAD` / `RWX` | identical | yes |
| phdr[0] offset / vaddr / align | `0x1000` / `0x680000` / `0x1000` | identical | yes |
| **phdr[0] filesz = memsz** | **`0x14a65e8`** | **`0x14a65f0`** | **+8 bytes** |
| SELF file_size | 10,866,322 | 10,867,186 | +864 bytes |

## 14.2 The headline result

**The 14.00 kernel's plaintext image is only 8 bytes larger than 13.52's** — same load
address (`0x680000`), same entry point (`0x6ffff0`), same single `PT_LOAD` segment, same
`RWX` flags. Meanwhile the encrypted container grew 864 bytes.

`phdr[0].filesz` = 21,652,968 bytes while the SELF is only ~10.87 MB — the segment is
therefore **compressed** (~2:1) before encryption. That single fact explains 14.3.

Conclusion: **14.00 is 13.52 with an extremely small, targeted change** — not a rebuild.

Caveat: this is a *size* fact. It bounds the change; it does not prove the bytes inside are
identical, and it says nothing about where the patch is.

## 14.3 Why nothing in the body is recoverable

332 probes of 96 bytes taken from the 13.52 encrypted body: **0 found verbatim in 14.00.**
Not even *unchanged* regions are detectable. Because the payload is compressed before
encryption, one changed instruction cascades through the whole compressed stream — so the
entire body differs even where the code is the same.

**Recoverable:** headers, entry point, segment geometry, exact plaintext image size.
**Not recoverable:** one byte of code.

## 14.4 The bootstrap question, answered

The user's hypothesis — "decrypt 13.52 fully, then use it to decrypt 14.00" — has a **correct
premise and a circular mechanism**:

* **Correct:** `key_type` is `0x0c01` for *both* kernels. One key opens both. Verified above.
* **Circular:** decrypting 13.52 requires *that same key*. No bootstrap — it is the identical
  problem twice, not a stepping stone.
* **Fatal:** the decrypted 13.52 kernel contains **no key material for its own SELF**.
  Decryption happens *before* the kernel runs (secure loader -> SAMU). The kernel is handed
  plaintext and never sees its key. So there is nothing inside 13.52's plaintext that unlocks
  14.00.

Also worth noting: the key banks are **per-module-class, not global** —
`80010001` = `0x0f01`, `80010002` = `0x0c01`, `80010006/8/9/A/B` = `0x0e01`. Three separate
banks. Holding the kernel key (0x0c01) would not by itself open the AuthMgr or the Secure
Loader.

**Net:** decrypting 13.52 is not a route to 14.00. It is the same lock, twice. But the 8-byte
size delta in 14.2 means a 13.52 disassembly maps almost directly onto 14.00 — which is what
makes the 13.52 dump worth having.

# 15. The asymmetry I failed to make clear: 13.52 is DUMPED, not decrypted

The confusion in "if we decrypt 13.52 fully, the same can be done with 14.00" is that it
treats the two kernels as symmetric. They are not. Two different statements:

**(a) "One key opens both."** TRUE, verified: `key_type = 0x0c01` for 13.52 and 14.00 alike.
If the 0x0c01 key is ever obtained, both kernels decrypt.

**(b) "Decrypting 13.52 is a step that enables 14.00."** FALSE. Because **nobody ever decrypts
the 13.52 kernel.** They *dump* it.

Why that changes everything:

| | how the plaintext is obtained | needs the key? | possible? |
|---|---|---|---|
| **13.52 kernel** | dump from RAM on a jailbroken console | **NO** | **yes, today** |
| **14.00 kernel** | must be decrypted (it never runs on our console) | **YES** | no |

The 13.52 kernel is **running in RAM in plaintext right now** on the user's console. The boot
chain already decrypted it. So you copy it out — no key involved. That is why plaintext 13.52
kernels exist in the scene and plaintext 14.00 kernels do not.

**So 13.52 is obtainable *without* performing the thing 14.00 requires.** They are not the same
task. Having 13.52 proves nothing about being able to reach 14.00.

And the plaintext itself does not help, because:

* SELF decryption happens **before** the kernel runs — on the SAMU secure loader. The kernel is
  handed plaintext and never sees its own key.
* The APU kernel holds only the **client** side: an authmgr mailbox wrapper, `verify_header`.
  It *requests* verification from the secure module; it does not hold key material.
* `getSealedKeySecret` is absent from the 13.52 kernel, and the EEKC store is empty on every
  boot (established earlier).
* Key derivation lives in the Secure Kernel / secure loader region (`80010001`), which is a
  *different* module under a *different* bank (`0x0f01`).

**Falsifiable test, if wanted:** dump the 13.52 kernel and grep it for key-derivation logic or
key material. If anything turns up, this section is wrong and section 14.4 needs rewriting.
Prediction: nothing will, because the key never reaches the APU.

# 16. "How do we get the key?" — the documented method, and the gate that stops us

Script: `probe_pih.py`, `probe_pih2.py`.

## 16.1 The community does not extract the key — it uses the console as an oracle

psdevwiki, *SELF - SPRX*, section "SELF Decrypter on PS4", states it outright:

> *"As PS4 SELF decryption keys are **not publicly known**, to decrypt SELFs, one can use his
> PS4 as a **blackbox**. There are some conditions: the SELF must have **valid signatures**, it
> must have a **required FW version lower than the FW version of the PS4 being used**, and for
> System SELFs the SELF **key_revision** must be according to the PS4 FW version."*

Tool: **AlexAltea's `self_decrypter.c`** — `orbital/tools/dumper/source/self_decrypter.c`.
We already have orbital locally at `orbital-ref/`, and have been building `selfdec2`. So the
oracle route is the one we were already on.

Corroborating (nextgenupdate, SAMU resource): *"Although we can interact with it to decrypt
almost everything it is impossible to extract any keys so that decryption could be done
externally."* And the PS4-side keys are **burned in the APU**.

## 16.2 Measured: the gate that closes on us

Program Identification Header, read from the two files (offset 0xB8, 0x48 bytes):

| offset | field | 13.52 | 14.00 |
|---|---|---|---|
| 0xB8 | Auth ID | `0x0000000000000000` | same |
| 0xC0 | Program Type | `0x3c00000000000001` | same |
| 0xC8 | Program Version | `12` | same |
| **0xD0** | **System SW Version** | **BCD `0x1352` = 13.52** | **BCD `0x1400` = 14.00** |
| 0xD8 | (same BCD version again) | 13.52 | 14.00 |
| **0xE0** | **Digest (0x20)** = SHA-256 of the **decrypted ELF** | `4cbd3e25…b1969fe3` | `a6691424…3fc9e38e` |

Applying the condition:

* SELF has valid signatures -> **yes** (a genuine Sony-signed SELF).
* **required FW (14.00) < console FW (13.52)** -> **FALSE.**
* System SELF key_revision vs console FW -> **fails.**

**The blackbox decrypter refuses the 14.00 kernel.** The blocker is a *version gate*, not a
missing key.

## 16.3 Why this is self-closing

The condition demands "required FW **lower** than the console's FW". To blackbox-decrypt the
14.00 kernel you therefore need a console running **>= 14.00 with a jailbreak**.

That is the exact thing that does not exist. And note the deeper consequence: **if you had a
>= 14.00 jailbroken console you would not need the key at all** — you would dump the running
14.00 kernel out of RAM, exactly as we do for 13.52.

**So the key is not gated behind searching. It is gated behind a 14.00 exploit.**

## 16.4 The three doors, and the wall behind each

| door | status |
|---|---|
| Extract the key from the SAMU / APU fuses | refused by architecture — *"impossible to extract any keys so that decryption could be done externally"* |
| Use the console as a blackbox oracle | **blocked by the FW gate measured above** (14.00 > 13.52) |
| Obtain it from whoever already has it | the leaked offsets imply such a party exists; not a route we can execute |

Historical note: flatz's Dec 2021 CCP bug *did* dump/bruteforce **key slots** — but it lived in
the **secure kernel** (SAMU-side access), was ~9.00-era, and is patched.

## 16.5 What we did gain

The **SHA-256 of the decrypted 14.00 ELF** is sitting in the clear in the SELF header:

```
a66914240c545e47b2850cc09690e010faa753e939db90245e224b3d3fc9e38e
```

That is a free **verification oracle**: any future candidate decryption can be checked against
it instantly, without the key. (It does not help *recover* the key — SHA-256 is one-way.)

Caveat on method: offsets above are derived by measurement plus the wiki's stated layout, and
the wiki's PIH description omits the extra BCD field at 0xD8 that we observe. Treat 0xD0/0xE0 as
empirically established, not copied.

# 17. Why brute force and fuzzing do not apply here

## 17.1 Fuzzing is not key recovery

Fuzzing finds **memory-safety bugs** — crashes, overflows, bad validation. It does not recover
cryptographic keys. There is no input that makes a correct AES implementation reveal its key.

And there is nothing on the PC side to fuzz. What we hold is a **ciphertext blob**. The parser
that owns the key runs inside the SAMU, on the console. Our machine has no code path that ever
touches the key, so there is no PC-side target to throw malformed input at.

## 17.2 Brute force: the search space is 2^128

The segment key is **AES-128-CBC** (psdevwiki, Segment Certification: *"AES Key | AES128CBC
Key for Segment 1"*).

```
2^128  =  340,282,366,920,938,463,463,374,607,431,768,211,456
       ~  3.40 x 10^38
Age of the universe ~ 1.38 x 10^10 years
```

| assumption | keys/sec | years to exhaust | in universe-lifetimes |
|---|---|---|---|
| perfect 1-block filter + top-tier ASIC | 10^9 | 1.1 x 10^22 | **780 billion** |
| generous ASIC farm | 10^12 | 1.1 x 10^19 | **780 million** |
| realistic — full 10.87 MB SELF decrypt + decompress + verify per candidate | ~1.5 x 10^3 | 7.2 x 10^27 | **520 quadrillion** |

The realistic row is the honest one: a candidate key can only be *tested* by decrypting the
whole segment (10,866,322 bytes = 679,145 AES blocks) and decompressing it. There is no cheap
early-out, because the payload is compressed, so the first decrypted bytes are not predictable.
That caps the practical test rate around **10^3 keys/sec**, not 10^12.

You would expect a hit at ~half the space. Same order of magnitude. **No filter, no GPU farm,
no ASIC changes this by enough to matter** — the gap is eleven orders of magnitude at best.

## 17.3 One interesting consequence

The SELF file is byte-identical on every console (it ships in the PUP). So the key that decrypts
the segment must be **static, not per-console** — otherwise the same SELF could not be decrypted
on different machines. That means a single successful recovery would unlock that bank for
**all** consoles and for **all** firmware using it (13.52 and 14.00 both name `0x0c01`).

That is exactly why the key is valuable, and exactly why it is not public, and — because it
would be a one-time cost for the entire scene — exactly the kind of thing that would long since
have been done if 2^128 were reachable by force.

(Note the tension worth flagging: psdevwiki's KeySlots lists a *per-console* layer, slot 6,
derived from slot 0, for the "Perconsole Layer of IPL". How that squares with SELF files being
identical across consoles is unresolved. It does not change the conclusion.)

## 17.4 Bottom line

Brute force is mathematically possible and physically not — by a margin so large it is not a
close call. **The key cannot be searched for; it has to be either handed to you by a console
running >= 14.00, or extracted from the APU with hardware.**

# 18. How a 14.00 exploit would actually be built (demystified)

Correcting the earlier "only by someone else" framing. The knowledge is not secret. It is a
public engineering pipeline with public parts.

## 18.1 The chain

```
userland entry  ->  kernel bug  ->  kernel R/W  ->  dump 14.00 kernel from RAM
```

Three links. Note again: **decryption never appears in this chain.** The decrypted kernel is the
*output*.

## 18.2 Link 1 — userland entry on 14.00: largely solved already

consolemods *PS4:Exploit_Chart*:

* **The Lua save-game exploit still works on the latest firmware** (Artemis-engine games;
  YARPE for Ren'Py). Also Mast1c0re (PS2 emulator), Netflix-N-Hack, BD-JB, WebKit.
* Caveat, stated on the chart for 12.50+: the **Poopsploit kernel exploit requires a specific
  privileged userland context** — *"which can only be accessed through Webkit, the PlayStation
  Vue application, the PS2 emulator, or BD-JB."* Lua alone does not provide it.
* 13.50/13.52 got the `rawgame4.github.io` WebKit exploit (that is the chain being used now).
* 14.00 is where the chain stops: **no public kernel exploit, and theflow's hypervisor bug was
  patched in it.**

So link 1 for 14.00 is plausibly available (WebKit class / BD-JB / PS2 emu). The gap is link 2.

## 18.3 Link 2 — the kernel bug: this is the real work, and the tooling just changed

**The decisive fact: the PS4 kernel is a FreeBSD fork, and FreeBSD's source is public.** Praetorian
states it directly: *"Sony's PlayStation is built on it."* You do not need the decrypted binary to
reason about the code — though it helps confirm.

Praetorian, *FreeBSoD* (17 Jun 2026) — an AI-assisted FreeBSD kernel bug hunt:

* Started *"poking at the FreeBSD kernel with Claude Code... a few days of work turned up real
  bugs and a weekend after that produced two working exploits capable of escaping from a
  FreeBSD jail."* ~8 vulnerabilities disclosed.
* Budget: **a single Claude Pro Max account, ~$100/month.**
* Methodology, which is the transferable part:
  1. Deep-research pass to build a **database of known FreeBSD kernel vulnerability patterns**.
  2. Have the agent **write CodeQL/semgrep rules** for those patterns -> *"thousands of candidate
     vulnerabilities."*
  3. **LLM triage** of candidates to reject false positives.
  4. **Feedback loop with a real oracle**: a **VM running the FreeBSD kernel built with KASAN**,
     used by the agent to test each hypothesis and iterate PoCs.
* They name the PS4/PS5 scene explicitly: *"These types of vulnerabilities are often exploited by
  the PS4 and PS5 jailbreak community as part of exploit chains... one chain leveraged a
  filesystem driver vulnerability alongside a WebKit vulnerability to fully jailbreak the
  console."*
* Concrete example, **CVE-2026-3038** (`sys/net/rtsock.c`, `rtsock_msg_buffer()`): user-controlled
  `sa_len` up to 255 copied into a 128-byte `struct sockaddr_storage` on the kernel stack — the
  guarding KASSERT **compiles out in production kernels**, and **`RTM_GET` is exempt from the
  `PRIV_NET_ROUTE` check, so any unprivileged local user can trigger it**.
* Honest failure modes they document: token limits, false positives, **sycophancy**, and the model
  *"cheating"* (e.g. patching the kernel to make a bug triggerable, or loading a kernel module
  containing the ROP gadget it needed). Mitigation they recommend: custom harness, a **judge/peer
  LLM**, and strict acceptance criteria.

## 18.4 Link 3 — why the 13.52 dump is step 3 of building the 14.00 exploit

We are about to hold a **plaintext 13.52 kernel**. And 14.00 vs 13.52 is **+8 bytes**, same load
address `0x680000`, same entry `0x6ffff0` (section 14).

Therefore a kernel bug found in the 13.52 image is **very likely still present in 14.00** unless
Sony's few-byte patch touched exactly it. The 13.52 dump is not a consolation prize — it is the
**local bug-hunting target** plus the **KASAN-VM comparison basis** for link 2.

## 18.5 Honest limits

* Sony's fork is **FreeBSD 9-era** (2012). Modern CVEs (like CVE-2026-3038, FreeBSD 14/15-era code)
  mostly will **not** map. The *methodology* transfers; the *specific bugs* largely do not.
* 13 years of Sony hardening on that fork. Mitigations are present (the article notes FreeBSD ships
  SMEP, SMAP, KASLR, canaries).
* It is still months of work for a person. It is not a weekend.
* Nothing here is reachable from inside this chat — it needs a console, a FreeBSD VM, and time.

## 18.6 Bottom line

Not secret knowledge, and not "someone else's". It is a **documented, public, and now partly
automated** pipeline: userland entry (exists for 14.00) + a FreeBSD-kernel bug hunt (public source,
AI-assisted methodology, ~$100/month, KASAN VM as oracle), with the **13.52 dump as the local
target**. The obstacle was never access to the knowledge. It is the months of work.

# 19. FULL 13.52 KERNEL DUMPED — done, clean, console alive

Payload: `kmemfull/` (new, purpose-built). Deploy script `go_kmemfull.py`.
Log: `kmemfull_run.log`.

## 19.1 What was built and why it is not kmemdump v10

`kmemfull v1` — new source (`kmemfull/source/main.c`), built in the same SDK
container as the previous payload (`docker run --entrypoint make ... ps4-payload-sdk:latest`,
image `ps4-payload-sdk:latest`, 616 MB, already present).

Differences from v10 that mattered:

1. **Continues past read failures.** v10 broke out of the loop. A single unmapped
   hole would have truncated the dump. Now holes are zero-filled (keeping the file
   address-aligned), counted, and the walk carries on.
2. **Full image window**, taken from two agreeing sources: the SELF program header
   (`p_vaddr 0x680000`, `p_filesz 0x14a65e8` -> `0x1b265e8`) and
   `include/offsets_1352.h` (`TEXT_BASE 0x0`, `DATA_FILE_END 0x1b265e8`).
3. **8-byte readability gate before bulk work**, so a bad base aborts cleanly.
4. Incremental writes, live status file, resumable via `kmemfull.cfg` `start=`.

Build note for next time: the SDK image's `/entrypoint.sh` has CRLF line endings, so
`exec /entrypoint.sh` fails with "no such file or directory". Use
`docker run --rm --entrypoint make -v <dir>:/kmemfull -w /kmemfull ps4-payload-sdk:latest`.

Build note 2: do not nest `/* */` inside a block comment — it closed the header comment
and broke the compile on the first attempt.

## 19.2 Result — clean, zero holes, no softlock

```
KMEMFULL v1: start
kbase        = ffffffffc5530000
gate ok      first8 = 7f 45 4c 46 02 01 01 09   (ELF64, LSB, EI_OSABI 9 = FreeBSD)

chunk          0x1000 (4096 B)
done           28468712 B   ok=6951   holes=0
```

* **28,468,712 bytes** written to `/mnt/usb0/kmemfull.bin`.
* **6,951 chunk reads, all successful, 0 holes.**
* **Console survived** — the 3232 log kept streaming normal SceShellCore /
  UIProcess activity after completion. No softlock.
* The first 8 bytes are the kernel's own **ELF64 x86-64 header with EI_OSABI = 9
  (FreeBSD)** — independent confirmation that `kbase` is the true image base.

**Chunk size answered:** 4096 B is safe. The 128 KiB copyout that killed the console

## 19.3 Scope — be precise about what this is

This is the **file-backed image**: `0x0 .. 0x1b265e8`, i.e. `.text`
(`0x0 .. 0xcfe758`), the gap, and `.data` (`0x1520000 .. 0x1b265e8`).

It does **not** include the runtime `bss` region beyond `0x1b265e8`, where the
AuthMgr/SBL runtime structures (`0x269c0a0` and friends) live. That region is mapped
and readable and could be captured in a second pass — but it is runtime state, not
kernel code, and is irrelevant for disassembly and bug hunting.

So: for the purpose this dump exists for — static analysis and the FreeBSD bug hunt —
this is the complete kernel.

## 19.4 Validation

`verify_kdump.py` — run it on the copied-off `kmemfull.bin`. It checks size, the ELF
header, the v9 `ORBISS` anchor at `0x1520000`, region behaviour, FreeBSD version
fingerprints, and PS4-specific symbols (`SceSblAuthMgr`, `sceSblAuthMgrIsLoadable`,
`SblDrvHdlrSx`, ...).

## 19.5 What this unlocks

With the plaintext 13.52 kernel in hand:

1. **Disassembly base.** 14.00 is 13.52 + 8 bytes, same load address, same entry
   point — a 13.52 disassembly maps almost directly onto 14.00.
2. **Bug hunt target** (section 18.3). The kernel is a FreeBSD fork with public
   source, so known-vulnerability-pattern rules can be run against this image, and
   candidates tested against a KASAN FreeBSD VM.
3. **Static confirmation** of everything previously inferred from live probing.

This is the first artefact in this whole investigation that actually exists on disk.
