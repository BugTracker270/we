## 1. What I verified on your console (raw evidence)

I read your console's secure-partition device nodes over FTP. All read-only.

### 1.1 The COREOS device hands you the firmware's secure modules — but *encrypted*

`/dev/sflash0s1.cryptx3` → an SLB2 container, 7 entries (`SLB2 v1 flags=0x0 file_count=7`):

| # | name | size | what it is |
|---|---|---|---|
| 0 | `80010001` | 98,672 | Secure Kernel |
| 1 | `80010002` | 10,866,322 | **the Kernel** (decompressed size 21,652,968) |
| 2 | `80010006` | 41,920 | secure module |
| 3 | `80010009` | 17,348 | secure module |
| 4 | `8001000A` | 25,524 | secure module |
| 5 | `80010008` | 88,304 | **AuthMgr — this is where the SELF keys live** |
| 6 | `8001000B` | 58,276 | secure module |

Their SELF headers are plaintext, e.g. entry `80010002` starts `4f 15 3d 1d 00 01 01 12 01 0c 00 00` → magic `4F153D1D`, program_type `0x0C` = **Kernel**. Entry `80010001` → program_type `0x0F` = **Secure Kernel**.

**But the segment bodies are encrypted.** Parsed straight out of the dumped bytes:

```
80010002 Kernel      : segs=1  seg[0] props=0x00040F enc=1 comp=1 offset=0x2B0
                       -> segment data first8 = 75 e0 2b c1 e3 29 0e db   (not ELF -> encrypted)
80010001 SecureKernel: segs=2  seg[0] props=0x000007 enc=1 comp=0 -> 97 85 1f 2f …
                                seg[1] props=0x100007 enc=1 comp=0 -> 75 2e 6d c5 …
```

`enc=1` on every segment = the `SF_ENCR` flag. So: **reading the device does NOT decrypt the kernel for you.** That closes off the "just read the flash" shortcut.

### 1.2 Both coreos copies are the same, still-wrapped thing
`/dev/sflash0s1.cryptx3` vs `/dev/sflash0s1.cryptx3b` = the active/inactive pair. Same 7 names, slightly different sizes, **both start with the SELF magic** — neither is a decrypted variant. No device on this console yields decrypted secure modules.

### 1.3 What *is* decrypted: the secure loader's header, and `/system`
`/dev/sflash0s1.cryptx2b` → SLB2, one entry `80000001`, 145,376 bytes, starting:

```
5e d7 9a 0b | 80 02 00 00 | 00 01 00 00 | 60 34 02 00
magic        header=0x280  entry=0x100   body=0x23460
```
That is exactly psdevwiki's Secure Loader layout (magic `5E D7 9A 0B`, header 0x280, body 0x23460), and 0x280 + 0x23460 + 0x100 footer = **145,376** = the SLB2 entry size exactly. So the header is plaintext, the body is "encrypted with two layers of AES-CBC". Al-Azif's `80000001.py` needs *this* file **decrypted** — the console gives it wrapped.

And separately: `/system/common/lib/*.sprx` come back as **plaintext ELF** (`7F 45 4C 46 02 01 01 09`). Your console *can* produce decrypted modules — for its own firmware.

## 2. So how does the kernel layer get broken? (the real mechanism)

From Al-Azif's own tooling, which is the authority here:

- `ps4-cfw-toolkit`: *"With the proper keys, **all of which can be obtained from the console**, you can decrypt AND properly encrypt: EAP KBL, EAP Kernel, EMC IPL, Syscon."* … and separately: *"SELF Files (Encrypted and signed with private keys) — **Private keys are NOT on the console**."* → the **RSA signing** keys aren't on the console. The **AES SELF decryption** keys are.
- `ps4-re-utilities` ships `80010008.py`: *"Automatically extracts **SELF keys** from a decrypted **AuthMgr** binary (80010008). It currently locates **key banks** by using the checksum of the first 0x10 bytes in each bank… reliably works for firmware versions 1.00 through 13.50."*
- The console-side SELF-decrypt protocol is a mailbox conversation with the auth manager (`AUTHMGR_CMD_VERIFY_HEADER` → `AUTHMGR_CMD_LOAD_SELF_SEGMENT` / `LOAD_SELF_BLOCK`) — visible in AlexAltea's `self_decrypter.c`.

Put those together and the working route is:

> decrypt PUP → get encrypted kernel SELF → **get the SELF keys out of a decrypted AuthMgr** → decrypt that SELF **offline on the PC**.

That last step has no firmware check whatsoever. The psdevwiki condition only bites the lazy route.

## 3. The methodology, staged

### Stage 1 — Decrypt the 14.00 PUP on your console  ✅ ready to run
What the payload does (from `andy-man` source, verified): opens `/dev/pup_update0` and drives the kernel's encrypt service (`ioctls 0xC010440D`, `0xC0184401`, `0xC0184402/03`, `0xC0184404`, `0xC0284405`), reading `/mnt/usb0/safe.PS4UPDATE.PUP` and writing `/mnt/usb0/<entry>.dec`.
Refusals are documented as **older-than-installed** and **wrong product code** only → 14.00 > 13.52 ✅, retail ✅.
Then unpack `PS4UPDATE1.PUP.dec` → COREOS image → inside it the same SLB2 shape I verified above, including the 14.00 `80010002` kernel SELF. **Still encrypted — but now in your hands.**

### Stage 2 — Get a decrypted AuthMgr (`80010008`)  ⚠️ the bottleneck
The console will not hand you this decrypted (verified: §1.1/§1.2). Two ways in:
- **(a) Build/obtain a SELF decrypter payload for 13.52.** The protocol is known and documented; AlexAltea's proof-of-concept is 1.76-era, so this means a build, not a download. It works because your console's *own* AuthMgr has required-FW 13.52 ≤ 13.52.
- **(b) Dump the loaded AuthMgr from kernel memory** (it is running, in plaintext). The payload SDK has `kpayload_dump`/`get_memory_dump` and the offset table literally annotates `MMAP_SELF_2/3` as *"Used in Module Dumper, App Dumper, and FTP"* — i.e. this class of tool exists.
Then run `80010008.py` → **SELF key banks.**

### Stage 3 — Decrypt the 14.00 kernel offline  ⚠️ unproven, but plausible
Feed the 14.00 kernel SELF + the extracted keys on the PC. Works **iff** 14.00's SELF uses a keyset revision present in a 13.52 AuthMgr's banks. psdevwiki's table:

```
| 1 | 3 | 13.00-13.04 |
| 1 | 4 | 13.50-??.?? |     <- open-ended; 14.00 may still be here
```
No keyset bump is documented after 13.50. That's the whole bet — and it is testable in one shot.

Then: `split_kernel.py` → FreeBSD kernel ELF + μBIOS → Ghidra.

## 5. "Is that really what I want?"

No — if what you want is the kernel, offsets are not the kernel. What they actually are:

- ~17 addresses a **payload** needs to exist: `XFAST_SYSCALL`, `PRISON_0`, `ROOTVNODE`, `COPYOUT`, `MMAP_SELF_1/2/3`, `DISABLE_ASLR`, `REG_MGR_SET_INT`, `SET_TIME`, `TARGET_ID`, `ICC_NVS_WRITE`, `NPDRM_OPEN/CLOSE/IOCTL`, `NO_BD_PATCH`.
- Enough to build GoldHEN-class tooling **the day 14.00 gets a JB chain**.
- **Not** enough to read the code: no functions, no bugs, no diffs, no Ghidra.

You want the binary — `80010002`, ~21.6 MB decompressed, FreeBSD-based, x86-64. That's Stage 1–3.
