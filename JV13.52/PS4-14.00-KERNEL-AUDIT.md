## 1. The one-line answer

**Half of what you want is possible, and the half that isn't is the half you actually asked for.**

| Layer | What it is | Can your jailbroken 13.52 console do it? |
|---|---|---|
| **1. PUP container + segments** | The outer encrypted update package (SLB2 → PS4UPDATE1/2.PUP → COREOS, SYSTEM, system_ex, EAP, EMC, syscon…) | ✅ **Yes** — this is the canonical "console as decryptor" method, and 14.00 (newer than 13.52, retail) satisfies the documented rules |
| **2. Kernel SELF inside COREOS** | The kernel is *not* plaintext in that segment — it is a still-encrypted **SELF** | ❌ **No** — blocked by a firmware-version condition (evidence in §4) |

So: **you can likely decrypt the 14.00 PUP. You cannot get a decrypted 14.00 kernel out of it today** — and no amount of tooling in this workspace changes that, because the blocker is not a missing tool, it is a console-side rule that only a console running ≥14.00 would satisfy (and 14.00 has no public jailbreak).

## 3. What the PUP actually is (verified from your file, byte level)

Parsed directly, not guessed:

```
PS4UPDATE.PUP  503,331,328 bytes
└── SLB2 container (magic "SLB2", version 2, file_count = 2)
    ├── entry 0  "PS4UPDATE1.PUP"  326,035,559 B  → header @0x400       (core: GameOS/kernel, syscon, bluray, EAP, EMC)
    └── entry 1  "PS4UPDATE2.PUP"  177,294,015 B  → header @0x136EEE00  (system_ex applications)
```
- Both fragment headers carry the PS4 PUP magic `4F 15 3D 1D` (also byte-swapped-releasable as `0x1D3D154F` in the payload source).
- Fragment sizes + padding reconcile to the file size → **container is complete, not truncated**. 480 MB is the normal size for a standard (non-recovery) update.
- **The firmware version is not readable offline.** It lives in `ScePupInfo.fw_ver`, which is inside the encrypted region (everything from `ScePupHeader+0x10` onward). Only the console can tell you. *(VERIFIED: psdevwiki PUP spec + the fact that the payload must call `encsrv_decrypt_header` before it can read the segment table.)*

## 4. Why the kernel layer is blocked (the decisive part)

This is the crux, and it is well documented:

**4.1 — The PUP decryption only opens the outer layers.** The community consensus on decrypted PUPs is that the inner executables are still encrypted. psdevwiki's SELF page confirms the kernel inside COREOS is a SELF with the *encrypted* flag set (`0x40F`: signed, **encrypted**, compressed, ordered). So "decrypt the PUP" ≠ "get the kernel".

**4.2 — The console's SELF oracle is firmware-conditioned.** From psdevwiki, [SELF - SPRX](https://www.psdevwiki.com/ps4/SELF_-_SPRX):

> "As PS4 SELF decryption keys are not publicly known, to decrypt SELFs, one can use his PS4 as a blackbox. There are some conditions: the SELF must have valid signatures, **it must have a required FW version lower than the FW version of the PS4 being used**, and for System SELFs the SELF key_revision must be according to the PS4 FW version."

A 14.00 kernel SELF has required-FW = 14.00. Your console is 13.52. 14.00 is **not** lower than 13.52 → refused. The "exceptions" the wiki mentions apply only to very early firmwares.

**4.3 — The keys are not public.** Same page: SELF decryption keys are not publicly known. `Al-Azif/ps4-cfw-toolkit` is explicit that for SELF files "Private keys are **NOT** on the console" — while EAP KBL / EAP Kernel / EMC IPL / syscon *are* obtainable from the console. And `Al-Azif/ps4-re-utilities` states plainly: "**The scripts require decrypted input files. You will need separate means to obtain these decrypted files.**" (That directly contradicts the previous session's claim that those utilities would perform the kernel-decryption step.)

**4.4 — And 14.00 can't be reached from the other side either.** 13.52 is the latest exploitable firmware; 14.00 is unexploited with no public kernel exploit, so nobody can run a payload on 14.00 to have it dump its own kernel. Chicken-and-egg.

**Net effect:** today, a decrypted 14.00 kernel cannot be produced from a 13.52 console by any documented route.

## 6. The one remaining technical path (unproven — flag it as research, not a plan)

There is a documented way to do SELF decryption **offline**, which would bypass §4.2's console-side firmware check:

- `Al-Azif/ps4-re-utilities` ships `80010008.py`: *"Automatically extracts **SELF keys** from a decrypted **AuthMgr** binary (80010008). It currently locates **key banks** by using the checksum of the first 0x10 bytes in each bank… reliably works for firmware versions 1.00 through 13.50."*
- If the offline SELF keys for the keyset revision used by 14.00 are present in a 13.5x-era AuthMgr, the 14.00 kernel SELF (once you have it from the decrypted PUP) could in principle be decrypted **offline on the laptop**, with no console involvement in that final step.

Why this is *plausible but not established*:
- ✅ psdevwiki's keyset table shows the system-modules keyset changed at **13.50 and the entry is open-ended** (`| 1 | 4 | 13.50-??.?? |`), i.e. **14.00 may still be on the same keyset revision as your 13.52 console**.
- ⚠️ It depends on (a) obtaining a **decrypted AuthMgr (80010008)** — it's a secure module inside COREOS, *not* in `/system`, so FTP cannot reach it; it needs a kernel-level coreos/memory dump, i.e. another payload and a genuinely new capability; and (b) the key banks actually covering 14.00.
- ⚠️ Nobody in this workspace has verified either half. I am **not** claiming this works.

**This is the only avenue I found that isn't already ruled out.** Everything else is closed.

## 7. What's actually worth doing

### 7.1 Free win — 14.00 kernel offsets already exist publicly
`Scene-Collective/ps4-payload-sdk`, commit `b732641` *"Add 14.00 support"* by Al-Azif, **19 Sep 2026** — 17 real `K1400_*` defines (e.g. `K1400_COPYOUT 0x002BD950`, `K1400_PRISON_0 0x0111FA18`, `K1400_MMAP_SELF_1 0x003B38A0`). These differ from 13.52's values (they're not copies), so *someone* has 14.00 kernel data. If your goal is "14.00 internals for porting prep", **you already have the addresses** without any of this.

### 7.2 Option A — finish the PUP decryption (low risk, real but limited payoff)
One action: launch `ps4-pup-decrypt.bin` on the console (menu → Payloads, or have me push it if 9090 comes back). What you get:
- ✅ **Proof of what your 480 MB file actually is** — after `encsrv_decrypt_header`, `ScePupInfo.fw_ver` becomes readable. This is the only way to confirm it's really 14.00.
- ✅ Decrypted segment images: COREOS, SYSTEM, system_ex, EAP/EMC/syscon/bluray firmware, watermark/EULA.
- ❌ The kernel stays an encrypted SELF. No 14.00 decompilation.
- Risk: low. Crash → reboot → re-run GoldHEN. **Never install the update.**

### 7.3 Option B — dump your own 13.52 kernel (the pragmatic RE target)
Your console can hand out decrypted modules for **its own firmware** right now (I already proved it). Getting 13.52's decrypted kernel ELF gives you a real, complete image to work in Ghidra **today**, and lets you diff it against the public 14.00 *offsets* to see what actually moved — which is most of what "14.00 porting prep" needs.

### 7.4 Option C — pursue §6 (research project, uncertain)
Needs a coreos/module dumper payload + offline key extraction + luck on the keyset. Multi-step, non-trivial, no guarantee.

## 8. Hard safety rules

1. **Do not install 14.00.** That is the one irreversible mistake here. Your console has no pending update staged (verified), and the USB file is named `safe.PS4UPDATE.PUP` so it won't be offered — keep it that way.
2. Your jailbreak is RAM-only; a reboot loses it and you re-run the 13.52 chain. Nothing I did requires a reboot.
3. Don't launch the payload on 9090 blindly without someone watching the console screen — you want to read the notifications (they name the failing step precisely).
4. Writing anything into `/system` to try to force SELF decryption is **not** recommended: it writes to flash and the firmware check would still refuse.
